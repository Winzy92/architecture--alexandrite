Мотивация:
Внедрение кэширование решит проблемы работы операторов с MES API.
Сейчас операторы сталкиваются со следующими проблемами:
1) высокая задержка при чтении данных;
2) отсутствие горизонтального масштабирования;
3) перегрузка MES DB;
4) рост RPS в случае увеличении количества операторов;

Все эти проблемы в конечном итоге сказываются на работе БП - медленная работа операторов - рост времени выполнения заказа и сокращение количества выполненных заказов. Некоторые пользователи увидев что заказ "повис" могут просто отказаться.
Т.е. существует реальный шанс потери заказов.
С помощью кэширования мы ускорим работу оператов и стабилизируем работу БП в их зоне ответственности.

Что кэшируем
Только наиболее "дорогие" и часто читаемые данные:
- Список заказов для оператора (фильтрация по статусам, сортировка по дате)
- Карточка заказа (основные атрибуты, текущий статус, любые данные которые редко меняются)

Не кешируем:
- Операции изменения статуса.
- Данные, требующие строгой консистентности (например транзакционные данные).

Предлагаемое решение:
Решение №1
1) Тип кеширования - Серверное кеширование.
 В архитектуре подразумевается несколько операторов, очевидно есть сложная логика фильтрации заказов и в случае реализации клиентского кэширования мы просто усложним ui, а нагрузка на сервер может сохраниться.
 В случае клиентского кэширования в данном случае мы не решим проблему в непосредственном месте.
2) Паттерн кеширования - Cache-Aside
Write-Through - в нашем случае будет увеличиваться задержка записи, т.к. при работе в MES идет активная смена статусов заказа.
Refresh-Ahead - мы не можем предсказать какие заказы будут нужны оператору.
Write-Behind - рост задержки записи (для нас это критично, потому что изменение статуса - критический момент для БП). Кэш в этом подходе является критически важным компонентом, если кэш упал то и MES лежит.
Read-Through - тут по сути кэш становится частью БП, кэш участвует в каждом чтении, если он недоступен, то MES лежит. Read-Through хорошо работает для простых запросов, у нас же оператор будет загружать и фильтровать списки.
Cache-Aside - данные кладутся в кеш только при чтении, при записи кэш инвалидируется, приложение само управляет кэшом.

В MES кеш не должен участвовать в пути записи данных, он должен ускорять только чтение.

3) Стратегия инвалидации кеша - Комбинированная
Программная инвалидация по событию изменения статуса заказа, дополнительная инвалидаци по времени жизни, на случай сбоев, аварий и тп.
С помощью временной инвалидации мы защищаемся от длительного использования устаревших данных, а основной механизм инвалидации идет по смене статуса.

Сравнительный анализ стратегий инвалидации кеша

| **Временная**                                                                                     | **Инвалидация основанная на запросах**                                         | **Инвалидация на основе изменений**                                                         | **Программная инвалидация**                                                            | **Инвалидация по ключу**                                                            |
| ------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| Простая и надёжная стратегия, не требует сложной логики и защищает от устаревших данных           | Позволяет обновлять кеш только при реальной необходимости чтения данных        | Гарантирует высокую актуальность данных при изменении состояния системы                     | Полный контроль над моментом и логикой сброса кеша                                     | Позволяет точечно очищать кеш без влияния на остальные данные                       |
| Данные могут быть неактуальны до истечения заложенной уставки по времени жизни, нужен ее подбор.  | После истечения кэша запрос будет медленный                                    | Нужны механизмы событий и контроль изменений.                                               | Необходимо реализация механизма в коде, ошибки в логике приведут к старевшим данным.   | Необходима схемы ключей, не удобен при массовой инвалидации.                        |
| Снизить нагрузку на БД без риска бесконечно устаревших данных                                     | При данном подходе лишний раз кэш не обновляется                               | Мы можем обновлять кеш сразу после смены статуса заказа                                     | В основном механизм чувствителен к человеческим ошибка при реализации.                 | Может обновлять только конкретный заказ или список заказов                          |
| Но данная стратегия не может обеспечить мгновенную консистентность.                               | Кэш не знает что заказ изменил статус, не реагирует на события.                | Нужна инфрастуктура событий, дополнительные затраты на ее реализацию.                       |                                                                                        | Сложно инвалидировать связанные агрегаты                                            |

Решение №2
1) Тип кеширования - Серверное кеширование.
2) Паттерн кеширования - Read-Through
3) Стратегия инвалидации кеша - по времени жизни.

|                      | **Решение 1**                                                                                                                                                                                                                                            | **Решение 2**                                                                                                                                            |
| -------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Описание решения** | MES при чтении сначала обращается к кешу (Redis). При отсутствии данных — читает из БД, кладёт в кеш. При изменении статуса заказа сервис явно инвалидирует данные, дополнительная инвалидация по времени для защиты пользователей от устаревших данных. | MES всегда читает данные через кеш. Кеш сам загружает данные из БД при отсутствии записи. Актуальность обеспечивается TTL.                               |
| **Плюсы решения**    | • Полный контроль актуальности данных<br>• Минимальное время рассинхронизации<br>• Хорошо отражает бизнес-события (изменение заказа)                                                                                                                     | • Проще реализация для команды<br>• Меньше кода в сервисе MES<br>• Меньше логики инвалидации                                                             |
| **Минусы решения**   | • Более сложная реализация<br>• Риск ошибки, человеческий фактор                                                                                                                                                                                         | • Возможны устаревшие данные до истечения времени жизни<br>• Первый запрос после истечения времени жизни — медленный<br>• Сложнее контролировать SLA     |
| **Риски**            | Ошибки в логике инвалидации                                                                                                                                                                                                                              | Устаревшие статусы заказов.                                                                                                                              |

Оба решения позволяют снизить нагрузку на MES и ускорить работу системы, однако Решение 1 лучше соответствует требованиям. Для MES важна актуальность статуса заказа, ошибки и задержки напрямую влияют на SLA и выручку.
Поэтому выбран подход с явной инвалидацией кеша при изменении данных, дополненный инвалидации по времени как страховочным механизмом. Это решение сложнее в реализации, но обеспечивает надежность и масштабируемость.
