Мотивация:
Сейчас яндекс метрики дают только сведения о действиях пользователей на сайте, но у нас нет информации о заказах оформленных через API, нет информации о сбое на этапе взаимодействия разных сервисов.
В результате пользователи недовольны, заказы где-то повисают, необходимо вручную искать и разбираться.
Внедрение мониторинга позволит:
1) Получать информацию о сбоях на всех уровнях взаимодействия сервисов, а также при выполнении каких-либо операций внутри сервисов. Это даст нам возможность оперативно реагировать, не давать повисать заказу. Время простоя и количество инцидентов снизится, пользователи получат свои заказы вовремя.
2) На основании информации о сборах в инфраструктуре или сервисах мы сможем планировать развитие продукта, мы сможем контролировать рост, в случае большого объема заказов во время распродажи мы увидим рост нагрузки, сможем принять меры для стабилизации работы системы.
3) Превратить систему из «чёрного ящика» в понятный процесс - мы будем видеть где системе не хватает устойчивости, позволит реагировать до того как пользователи массово ощутят проблему.
4) Повысим скорость релизов, с качественным мониторингом мы сможем быстро понять в чем проблема, быстрее подготовить обновление (или откатить текущее). Релизы становятся чаще и стабильнее.
5) Видеть количество заказов которое реально создается, сколько в итоге доходит до производства и доставки, где происходят потери. Т.о. мы сможем провести анализ, улучшить процесс и повысить прибыль.

Выбор подхода к мониторингу:
1) Shop API - Red + Use:
 - Number of requests (RPS) - Реальная нагрузка (endpoint, operation_type)
 - Response time (latency) - Идентификация медленного заказа (endpoint, quantile)
 - Number of HTTP 500 - Потерянные заказы (endpoint, error_type)
 - Number of simultanious sessions for shop API - Прокси-метрика пользовательской активности (channel)
 - CPU % for shop API - использование CPU, идентификация высокой нагрузки (instance_id, env)
 - Memory Utilisation for shop API - использование памяти, идентификация высокой нагрузки (instance_id, env)
2) MES - Red + Use:
 - Number of requests (RPS) - Реальная нагрузка (endpoint, operation_type)
 - Response time (latency) - Идентификация медленного заказа (endpoint, quantile)
 - Number of HTTP 500 - простой производства (endpoint, error_type)
 - CPU % for shop API - использование CPU, идентификация высокой нагрузки (instance_id, env)
 - Memory Utilisation for shop API - использование памяти, идентификация высокой нагрузки (instance_id, env)
3) CRM API - Red + Use
 - Number of requests (RPS) - Реальная нагрузка (endpoint, operation_type)
 - Response time (latency) - Идентификация медленного заказа (endpoint, quantile)
 - Number of HTTP 500 - Заказы не дошли до производства (endpoint, error_type)
 - CPU % for shop API - использование CPU, идентификация высокой нагрузки (instance_id, env)
 - Memory Utilisation for shop API - использование памяти, идентификация высокой нагрузки (instance_id, env)
4) Db - Use
  - Number of connections for db instance - проблем с пуллингом (db_name, env)
  - Memory Utilisation for db instance - использование памяти, идентификация высокой нагрузки (db_name, env)
  - Size of shop db instance - предотвращение аварий по диску (db_name, env)
5) RabbitMQ
 - Number of message in flight in RabbitMQ - идентификация заторов (queue, routing_key)
 - Number of dead-letter-exchange letters in RabbitMQ - потерянные события (queue, reason)
6) Дополнительные метрики
 - Orders by status - видим зависшие заказы (status, service)
 - Time in Status (Histogram) - сколько выполняется по времени каждый этап исполнения заказа (status, service)
 - CorrelationId - сквозной id заказа, прокидывается через всех участников процесса, видно всю цепочку событий.
 - Integration error rate - отлов проблем между системами

 1) Создать инстанс time-series базы данных для хранения технических и бизнес-метрик. Использовать Prometheus как сборщик метрик.

 3) Добавить сбор метрик в Shop API, MES, CRM.

 8) Обеспечить трассировку. В логах должна быть видна последовательность событий для correlationId.

 Показатели насыщенности:
 1) Для API:
  - CPU > 70% более 5 минут - скорее всего при такой нагрузке начнутся ощутимые задержки в работе API. Добавить оповещение уровня Warning, тикет devOps'у.
  - p90 latency > 2 секунд более 10 минут - метрика будет отображать проблемы с API 90% запросов должны укладываться в рамки до 2х секунд, дальше растет вероятность что пользователи начнут повторно "тыкать" и обновлять страницу, в итоге отказаться от заказа. Оповещение уровня Critical, тикет devOps'у.
  - комбинированный показатель latency + RPS. Рост обоих параметров будет говорить о возрастании нагрузки (например распродажа) и система перестает с ней справляться. Нужно уведомление уровня warning, тикет devOps'у, нужно масштабирование.
 2) БД:
  - Connections > 80% лимита - возрастает риск отказа всех сервисов, оповещение уровня warning, необходимо включение read-replica.
  - Disk usage > 75% - риск приостановки работы БД. Оповещение уровня warning,  тикет devOps'у.
 3) RabbitMQ:
  - Dead-letter-exchange > 0 - потеря события в очереди, ведет к прямым убыткам, это недопустимо. Уведомление уровня critical. Тикет в команду разработки.
  - Messages in flight > N - где N - это некая уствка выше которой мы считаем что потребитель сообщений очереди не справляется с нагрузкой. Характеристика забивания очереди сообщениями. Уведомление уровня warning, тикет в команду разработки.
