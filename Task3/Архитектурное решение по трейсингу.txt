Критические точки, где заказ может зависнуть или сломаться:
1) Переход SUBMITTED (Shop API) -> PRICE_CALCULATED (MES) - потенциальная проблема - в результате таймаута цена может не рассчитаться, заказ повиснет.
2) Переход MANUFACTURING_APPROVED (CRM) -> MANUFACTURING_STARTED (MES) - оператор может не подтвердить заказ, в силу человеческого фактора заказ может провисеть достаточно долго.
3) CRM. Закрытие заказа итоговое может завершаться в ручную, т.е. статус заказа может не меняться долгое время.
4) MES. Во время цикла производства заказ проходит различные состояния и может не меняться долгое время или повиснуть.
5) RabbitMQ. В случае если идет потеря сообщений очереди, или же наоборот потребитель не справляется.

Итого трейсингом покрываем:
1) Shop API
2) MES API
3) CRM API
4) RabbitMQ (producers + consumers)

Данные которые должны быть в трейсинге:
1) correlation_id - сквозной технический идентификатор, по которому можно понять что происходило с заказом на разных стадиях.
2) order_id - бизнесовый id заказа.
3) service name - имя сервиса (MES, Shop, CRM)
4) status - статус заказа
5) HTTP method - метод сервиса
6) status code - статус выполнения
7) channel (shop / api) - заказ может быть сделан как через магазин так и через API.
8) created - метка времени.
Для RabbitMQ:
9) message_id - id сообщеня в очереди
10) queue name - имя очереди
11) waiting time - время ожидания в очереди.

Мотивация:
Сейчас много времени уходит на разбор инцидентов, надо шерстить логи каждого сервиса в поисках ошибок, сопоставлять временные метки и тп. В целом весь БП обрабатывают "черные ящики".
Трейсинг сделать путь заказа максимально прозрачным и измеримым.
В итоге бизнес получит следующие преимущества:
1) Снизится время поиска причин и устранения проблем с зависшими заказами.
2) Позволит быстро выявлять проблемные места в цепочке, принимать упреждающие решения, в том числе позволит бизнесу расти.
3) Увеличится качество релизов, так как улучшится отладка БП на этапе разработки.
4) Уменьшится количество потерянных и проблемных заказов.
5) Можно прогнозировать задержки производства по тем или иным причинам, уведомлять об этом пользователей. 

Технические метрики:
1) p90 / p95 latency по цепочке заказа
2) Количество ошибок
3) Время ожидания в очередях

Бизнес метрики:
1) Orders stuck > SLA
2) Время обработки заказа (End-to-End)
3) Drop-off rate между статусами

Предлагаемое решение:
1) OTel SDK устанавливаем в Shop, MES, CRM
2) OTel Collector — централизованный сбор
3) Jaeger — хранение и визуализация трейсов
4) При создании заказа в Shop создается correlationID, который прокидывается во все сервисы.
5) CorrelationId записывается в headers RabbitMQ.
6) Измененная диаграмма С4 [C4_with_OTEL].

Компромиссы:
Трейсинг может быть неэффективен в следующем случаях:
1) Наличие ручных операций
2) Внешние системы, которые мы используем, но не контролируем и не можем изменить.
3) Легаси код. Его доработка может стоить очень много времени.

Безопасность:
1) Аутентификация в UI трейсинга
2) Внедрить RBAC, сделать пользователей с правами readOnly.
3) Ограничение доступа по VPN.
4) Все данные должны быть обезличенны, доступ к фалам моделей закрыт, если есть необходимость предоставлять какие-то чувствительные поля, то их надо маскировать.

Автоматический мониторинг процесса прохождения заказа
В разделе предлагаемое решение в принципе уже описано решение по correlationId, в разделе "Данные которые должны быть в терйсинге" указан service_name,
дополнительно предлагаю добавить метрики:
1) waiting time - уже описан в разделе выше.
2) Время обработки заказа (End-to-End) - уже описан в разделе выше.
3) Time-in-status - время нахождения в каждом статусе.

Настроим автоматический alert при следующих условиях:
1) Time-in-status > SLA -> тикет на разработчиков, ссылка на трейс.
2) p90 / p95 latency > x, рост времени выполнения этапа -> сигнализация (warning) для devOps и разработчиков.
3) N заказов за период превышают SLA - массовые задержки, возможно проблемы с инфраструктурой -> сигнализация для devOps, возможно необходимо уведомить бизнес о временных задержках.
