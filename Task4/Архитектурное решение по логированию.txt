Анализ системы в контексте логирования:
Логирование необходимо включить во всех системах, участвующих в БП:
1) Shop API
2) MES API
3) CRM API
4) RabbitMQ

Список обязательных логов уровня INFO:
1) Работа с заказом (Shop / MES / CRM)
 - Cоздание заказа, параметры - correlationId, orderId, user_id, source, created, method http (или event);
 - Изменение статуса заказа, параметры - correlationId, orderId, source, method http (или event), old_status, new_status, operatorId (может быть nullable), userId (может быть nullable);
 - Отправка запроса в другую систему, параметры - correlationId, orderId, source, method http (или event)
2) RabbitMQ
 - публикация сообщения в RabbitMQ, параметры - correlationId, orderId, message_id, queue, method http (или event);
 - обработка сообщения, параметры - correlationId, orderId, message_id, queue, method http (или event), processing_time_ms;
3) Пользовательские действия
 - действия операторов в MES, параметры - correlationId, orderId, operator_id, method http (или event);
 
Использование других уровней логирования:
1) Логи уровня ERROR - будем использовать при критичных сбоях, невозможности выполнить какого-либо этапа БП, потери данных, сбое интеграции. Используем их для формирование алертов. Всегда должны содержать correlationId, orderId.
2) Логи уровня WARNING - будем использовать при нештатных ситуациях, но не оказывающего критического эффекта на БП, например таймауты, ретраи (если конечно доработать альтсценарии), некорректные входные данные (опционально).
3) Логи уровня DEBUG - логи не включаются в продакшен, уровень используется только при отладке БП, может быть включен временно или при локальной отладке.

Мотивация:
Эффект для бизнеса:
1) Снижении затрат времени на разбор инцидентов.
2) Повышение качества продукта, из-за более качественной отладки БП, снижение количества обращений в поддержку.
3) Контроль SLA по показателям.
4) Рост клиентской базы из-за повышения качества продукта.

Технические метрики:
1) MTTR (mean time to recovery) - среднее время восстановления работоспособности системы после инцидента. Тут подразумевается БП целиком, т.е. если какой то из сервисов перестал отвечать, или дает всегда 500ку, в расчет идет время когда восстановится работоспособность всей цепочки.
2) Количество инцидентов без явной причины
3) Количество повторных багов

Бизнес-метрики:
1) Время ответа поддержки клиенту
2) Процент заказов, разобранных без участия разработчиков
3) Количество обращений в поддержку.

Приоритет внедрения логирования и трейсинга:
В первую очередь обязательно необходимо покрыть Shop API и MES API, тут происходит потенциально наибольшее количество проблем.
Ко второму приоритету можно отнести CRM API, RabbitMQ consumers.
Остальное (логирование уровня БД, расширение трейсинга и тп) в трейтьем приоритете.
Сначала логирование ключевых бизнес-событий и трейсинг критических цепочек.

Предлагаемое решение:

1) Технологический стек
 - Structured logging (JSON)
 - Log collector (Fluent Bit)
 - Log storage & analysis (OpenSearch)
 - Визуализация - OpenSearch Dashboards
 
2) Политика безопасности логов:
 - запрещено логировать платёжные и персональные данные в открытом виде;
 - для логирования чувствительных данных использовать маскирование и хэширование;
 
3) Доступ к логам:
 - доступ по VPN;
 - только сотрудники компании, реализовать RBAC, например Support — read-only, DevOps / Dev — расширенный доступ

4) Политика хранения логов:
 - контроль размера - rollover по размеру и времени;
 - отдельный индекс на каждую систему;
 - retention в зависимости от уровня логов, например WARN / ERROR — 21 день, INFO — 14 дней;
 
Логирование и анализ:
1) Алертинг:
 - Рост error rate.
 - Всплеск сообщений уровня warning.
 - Отсутствие ключевых событий цепочки БП. Т.е. например заказы создаются, но не передаются в производство и тп. Сигнал о том что БП фактически остановился.
2) Поиск аномалий:
 - резкий рост количества заказов;
 - аномальное число ошибок;
 - всплеск логов от одного IP;
 
Реакция - автоматический алерт, уведомление DevOps, наложить временные ограничения.

Критерии выбора технологии логирования:

| Критерий                             | ELK (Elasticsearch + Kibana)  | OpenSearch     | Splunk                    | 
| ------------------------------------ | ----------------------------- | -------------- | --------------------------| 
| **Лицензия**                         | Elastic License (ограничения) | Apache 2.0     | Проприетарная             | 
| **Стоимость поддержки**              | Средняя → высокая             | Низкая         | Очень высокая             | 
| **Поддержка structured logging**     | Да                            | Да             | Да                        | 
| **Поиск и аналитика**                | Сильные                       | Сильные        | Сильные                   | 
| **Масштабируемость**                 | Горизонтальная                | Горизонтальная | Горизонталья/Вертикальная | 
| **Интеграция с Fluent Bit**          | Да                            | Да             | Да                        | 

1) Как правило на небольшие проекты хватает бесплатных версий, но с ростом продукта возникает необходимость масштабирования и стоимость лицензии играет роль, т.к. это дополнительные издержки для бизнеса:
 - ELK — ограничения на коммерческое использование
 - OpenSearch — полностью open-source (Apache 2.0)
 - Splunk — закрытая лицензия, платно за объём логов.
OpenSearch будет лучшим выбором.

2) Стоимость поддержки, например для александрита, где в команде всего 1 DevOps, это критичный показатель. Предлагаю в критерии учитывать:
 - время DevOps'a
 - поддержка
 - инфраструктура
ELK - с ростом продукта будет стоимость поддержки будет расти.
Splunk - дорого уже на старте.
OpenSearch - дешевле по сравнению с конкурентами.

3) Поддержка structured logging (JSON) - позволяет фильтровать по correlationId, строить алерты, удобно искать ошибки.
Все продукты его поддерживают.

4) Возможности поиска и анализа.
Чем больше возможности тем легче разбирать инциденты.
OpenSearch / ELK / Splunk — полнотекстовый поиск, агрегации.

5) Масштабируемость, в случае роста нагрузки, будет критично.
Splunk хорошо масштабируется, но за это надо нести дополнительные расходы времени DevOps и денег (в нашем случае это минус).
OpenSearch масштабируется горизонтально и проверен на больших объёмах.

6) Интеграция с существующим стеком, легче интегрировать то что совместимо, минимальные затраты времени на реализацию.
Все продукты совместимы с Fluent Bit, преимущество будет за OpenSearch.
Fluent Bit + OpenSearch — нативная и стабильная связка, хорошо ложится на Kubernetes / EC2.
